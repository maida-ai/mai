# Authority platform qualification

Authority commands require Git 2.40 or newer. `mai init` checks the actual executable selected by PATH and exercises `merge-tree --write-tree --merge-base=<base>` in a disposable bare repository. Missing, non-executable, old, malformed and failed executables return installation or repair guidance before destination initialization. Apple Git is evaluated by its actual version and behavior; no bundled Apple Git version is assumed. An explicit-base merge failure has no implicit-base fallback because that could replay a submitted parent's delta after squash landing. Git client push/fetch capability and authority requirements are separate; the 2.40 requirement applies to the authority.

`cargo test --locked --test platform` exercises the installed Git against disposable repositories. It verifies explicit-base merge output, proc-receive dispatch with rejection and absent submission ref, and a successful push with a verified push option to a retained incoming ref. This is local file-transport capability evidence, not remote authentication, complete packet-line registration, network transport or crash-durability qualification. The incoming-ref fallback can acknowledge transport success before registration; future receive code must retain that ref, register/reconcile separately and never report transport success as queue admission. If required push-options are absent, submission admission must reject rather than silently dropping identity or options. Neither receive path is enabled by this batch; authority initialization retains its rejecting receive hook.

The ordinary native CI matrix uses current stable Rust and the runner's installed Git on Linux, macOS and Windows. Linux and macOS are intended first-class platforms. Windows remains best-effort pending native results for the exact implemented path; a Linux pass does not qualify Git for Windows, hook shell behavior or a Windows minimum-version combination. The minimum Linux CI job builds the exact Git 2.40.0 archive with its verified SHA-256 and tests Rust 1.85.0 using `--locked`. Current native versions and exact minimum combinations are separate evidence. Hosted jobs need to complete before claiming their results; workflow configuration alone is not a successful qualification.

All correctness jobs have a 20-minute bound, use locked Cargo resolution and read-only repository permissions. The minimum Git download has a 90-second request bound and two retries; the checksum mismatch fails closed. Existing experiment workflows remain manual-only; none is dispatched by these checks. `python3 scripts/check_qualification.py` checks offline locked dependency metadata against reviewed permissive license expressions and registry sources, with a 90-second subprocess limit, and checks workflow timeout, experiment-trigger and artifact-retention policies. The dedicated five-minute CI job fetches locked metadata first with bounded retries; Python is CI/development tooling, not a product runtime requirement. This policy guard is not a full YAML validator, vulnerability scanner or license-text audit. Changed license expressions require explicit review rather than an unbounded automated upgrade. No production dependency or license exemption is added here.

## Local Linux evidence

The implementation was checked on Linux with rustc 1.97.0 and Git 2.43.0: formatting, strict all-target locked Clippy and all-target locked tests passed. The kernel.org Git 2.40.0 source archive was downloaded, its SHA-256 `b17a598fbf58729ef13b577465eb93b2d484df1201518b708b5044ff623bf46d` verified, and its installed binary reported exactly `git version 2.40.0`. With that binary first on PATH, Rust 1.85.0 built and passed the all-target locked suite; the final platform regression additions also passed that exact minimum combination. No dependency changes were needed. Existing Unix socket tests required execution outside the restricted local-socket sandbox. Hosted native and minimum CI runs remain pending publication; these local results do not establish macOS or Windows support.
