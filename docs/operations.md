# Operations and recovery

[ADR 0010](adr/0010-staged-mvp-qualification.md) controls MVP scope. Priority, speculative/batch tuning and automated fix-forward examples below remain deferred proposals, not required or enabled initial MVP behavior. The initial queue is single-class and dependency-aware; core validation, ownership and recovery correctness remain mandatory. Priority RFC #93 and feature-specific tests precede future enablement.

**Current scope.** The old worktree engine is retired. This MVP layer provides persistence, authority administration, bounded validator slots, explicit receive and serial named-generation integration. The full automatic queue, drafts and safe sync are not available. See the [current CLI reference](cli.md) for the implemented surface; the current receive/integration contract is documented separately in [receive](receive.md). Recovery tiers, retention and forge operations below remain target mechanisms, not claims of operational readiness.

## Lifecycle and trust

One `mai serve PROJECT --foreground` engine owns each authority, enforced by an exclusive OS lock before database opening and startup reconciliation. `mai status PROJECT` can autostart it; `mai stop PROJECT` requests graceful shutdown. Clients use a Unix socket or native Windows named pipe; native platform CI must qualify behavior. Stale PID metadata never establishes ownership, and the persistent lock file is never deleted. The initialization hook rejects every receive until explicit enablement, regardless of engine readiness. Integration can block other engine requests while the gate runs; a client timeout does not cancel the active operation. An interrupted validator can retain an occupied claim requiring trusted inspection before reuse. See the [engine guide](engine.md) for the implemented surface and bounded startup behavior.

Authority qualification targets Linux and macOS with Git ≥ 2.40; S1 records Windows behavior and a receive fallback. Verify the installed Git rather than assuming a system-supplied version. Initial object format is SHA-1; imports with SHA-256, submodules or LFS reject clearly. Local alternates depend on authority object retention. Loopback tokens are a local transport boundary, not a multi-tenant service. Never mount the authority writable into agent containers.

## Diagnose current outcomes

Preserve the authority and agent workspace before attempting recovery. Keep the change ID, generation, command and exact error/result JSON. Use `mai show PROJECT CHANGE --generation 1 --json` to inspect the durable submission; exit 0 means the query succeeded. `state.kind=received` with a dependency list is normal before explicit integration. No background scheduler will advance it. A terminal `landed` outcome identifies the accepted commit and revision; a terminal rejection is immutable.

| Observation | Supported next action |
| --- | --- |
| Push response lost or timed out | After the engine can answer, inspect the same change identity or retry the identical commit with the same declared agent. A new commit is not needed just to recover the acknowledgment. |
| Integration deadline elapsed | Do not assume cancellation or start a competing recovery operation. The engine may still be running the gate. Once it can answer, inspect that generation and preserve its result. |
| `awaiting_approval` | Have the authorized reviewer inspect the returned exact candidate and binding. After an explicit decision, rerun integration of the same generation. Changed trunk/policy invalidates prior approval. |
| Lease or unresolved-parent preflight failure | Inspect the named lease/dependency. Supply the current owner claim or integrate the pending parent when appropriate; do not bypass another owner's lease or delete its state. |
| Terminal check/conflict/policy rejection | Inspect the reason and available bounded diagnostics/candidate ref. Correct the work as a new change from an appropriate accepted base; repeated integration cannot turn the rejected generation into a pass. Keep the original clone and submitted objects. |
| Infrastructure error or uncertain publication | Preserve evidence, establish whether the owner is still running, and reconcile through engine restart after it has stopped. Query the same generation before deciding whether another integration attempt is needed. |
| Occupied validator claim after interruption | For opted-in Linux supervision, stop the owner, inspect the claim and use [explicit recovery](validator-recovery.md) only with its verified cleanup receipt. Missing proof remains a preserved blocker; PID absence is not evidence of cleanup. |
| Unsupported format, missing lease state or contradictory evidence | Preserve the entire authority for diagnosis. Do not recreate its database, remove ownership files, replace lease state or move trunk to make startup pass. Older disposable evaluation state has no migration. |

During integration the single writer also serializes status, receive, approval and lease requests. Their shorter IPC deadlines can expire while work is still active; an unavailable status response alone does not prove the engine died. Inspect `.mai/engine.log` and any existing foreground/supervisor output. Use `mai status PROJECT --no-autostart` when checking availability without launching an owner. If a known owner has exited, normal `mai status PROJECT` or `mai serve PROJECT --foreground` starts ownership/reconciliation. Do not use a second writer or manually remove locks to force progress. The explicit `validator inspect` and `validator recover` commands also require exclusive authority ownership; use the [recovery guide](validator-recovery.md) before restarting an interrupted owner.

Opted-in Linux validation uses a separate worker that can finish native cleanup after engine death and retain an exact claim-bound receipt. The [explicit recovery procedure](validator-recovery.md) validates that proof and quarantines interrupted state before reuse; it never skips revalidation. A killed worker, legacy claim, changed boot or missing proof can still leave a single-slot authority blocked. Removing its marker would discard evidence without establishing quiescence. Creating another authority on the same machine also does not prove safety because its gate can reuse ports and external services. No universal recovery or measured MTTR target is claimed.

## Implemented reconciliation and its limits

Git's first-parent trunk is the acceptance ledger; SQLite records submission and validation state. Receive retains `refs/mai/changes/<change_id>/<generation>` before acknowledgment. Startup verifies exact submitted identities, candidate/tree/parent/policy evidence and revision trailers. It can complete an interrupted recognized publication or retire an unlanded interrupted attempt without creating a second terminal outcome. Contradictory or missing evidence refuses recovery rather than inventing a pass. Reconciliation of metadata does not establish that an interrupted validator's descendants have stopped, so an occupied slot may still require inspection before reuse.

Finite tests kill processes at selected receive/publication boundaries and restart to check retention and convergence. They do not establish power-loss durability, disk-controller ordering, recovery from arbitrary filesystem corruption or every possible interruption. Successful restart is also not a tested backup/restore procedure. Preserve failure evidence and report the exact phase when an unqualified path is encountered.

## Proposed automatic recovery — unavailable

There is no automatic fix-forward lane, culprit attribution, recovery deadline or compensating-revert policy enabled today. Pipeline invalidation and automatic retry/flakiness handling remain future mechanisms; no pass may authorize a different tree. The normal gate and work preservation remain requirements for any future path.

The optional M1b full tier confirms a nonflaky culprit by rerunning before and after it, then opens an owned conflict record with logs, the culprit manifest and a temporary `sev` grant. Recommended recovery gives that agent a bounded fix-forward window: the `mai.fixes=<change>` submission runs the normal gate, lands at severe priority and requires full confirmation inside the same recovery deadline; a gate pass alone never establishes green trunk. Expiry or the configured failed-gate attempt budget triggers a compensating revert through the same gate, with evidence and affected pending dependency re-evaluation. Already-landed dependents require an explicit compensation plan and must never be blindly replayed or duplicated. A failed full confirmation is not recovery and does not reset the deadline. If the revert conflicts or fails, freeze and notify the configured owner. Immediate `revert`, `freeze` and `continue` remain explicit alternatives; default policy and S4 window selection are pending. History is never rewritten. An upstream-sync conflict has a configured resolver; unrelated queue work can continue against the last synced base.

## Backup and restore qualification — pending

Back up `authority.git`, `.mai/state.db`, `.mai/leases.db`, gate evidence and required engine configuration as a coordinated recovery point. A safe procedure must quiesce intake and the writer, checkpoint or consistently copy SQLite including WAL state, preserve refs and objects, and protect token material separately from shareable archives. A live directory copy is not a proven consistent backup. The backup/restore issue must qualify restore into an isolated location, engine reconciliation, pending changes, drafts and validation evidence before claiming recoverability. No implemented backup command is promised yet.

## Retention proposal and current capacity bounds

Automatic change-ref pruning and draft retention are not implemented. The proposal retains change refs for a configured interval after terminal outcomes and drafts while registered and afterward; concrete durations are not chosen. Do not prune objects still needed by queues, dependency chains, candidates, drafts, evidence or alternates-backed clones. Future maintenance must run during safe idle periods. Workspace removal requires explicit handling of dirty files and pending/draft work rather than unconditional deletion.

Bound validator count, output, receive sizes and changed-path counts. Warm slots re-bootstrap when configured inputs change. Each gets a private temporary directory, `MAI_SLOT` and `MAI_PORT_BASE`; suites must use these for ports and databases because mai does not sandbox tests. Measure bootstrap separately from checkout and gate runtime before adding materialization machinery.

## Metrics and escalation

The proposed `mai status --metrics` reports p50/p95 recovery time from rejection to relanding and breakage detection to green; death-to-resumed-landing starts in M4. Track full-tier failures per landed change and revert rate as trunk guardrails. Split time to land into queue wait and validation; report gate duration, slot utilization, discarded speculation, outcome reasons, flaky rate and human interventions including priority grants. Report time to land per class, lease preemptions, aging promotions, and in-window fix-forward success versus reverts. Add scope-drift rate from M2 and late-conflict waste in M3 and resume success in M4. These metrics are currently unimplemented and unmeasured.

Capture reproduction refs, configuration hash, tree identity, attempt results and a bounded log tail for diagnosis. Do not expose tokens or raw agent context in diagnostics. Human approval is required for protected policy changes; models may escalate conflicts but never approve or accept them. Qualification evidence and current failures belong with implementation work, not a claim that the design has already achieved its targets.

## Manifests and priority operations

M1 computes file-unit manifests against the submitted base at receive and against the actual parent at landing. Keep `refs/notes/mai-objects` and the `state.db` unit index consistent with accepted history and include them in backup/reconciliation tests. `Mai-Objects:` lists up to 20 units, otherwise records a count and note pointer. Parser versions and explicit fallback reasons accompany later M2 object units. Agent-declared `mai.touches` is intent, not authoritative evidence. Manifests help diagnosis and affected-test selection; they never independently approve correctness.

Use the proposed `mai priority grant <agent|change> <class> --reason ... --ttl ...` and `mai priority revoke` interfaces only after implemented. Grant actors and revoke selectors still need qualification; do not assume a token has grant authority. Audit expiry, inheritance, severe in-flight caps and aging. Lease transfer/preemption after notice and grace is a future policy, not an ordinary lease command available today. Priority conflict winners determine which side resolves; they do not silently replace or discard the other side's work. Only severe work may cancel lower-class speculative candidates, whose submissions remain queued for rebuild. `mai log --object <unit>` is the planned history lookup.

## Continue local work after landing

Use [copy-based continuation](continuation.md) for an explicit landed generation and clean unregistered linear suffix. It preserves the old clone and creates a new workspace on a pinned accepted trunk. Dirty/untracked source, registered suffix commits and ambiguous ancestry refuse; ignored files remain in the source and are not copied. A failed or interrupted destination is evidence, not a retry target: preserve it and choose a new path. In-place sync, autostash and automatic conflict resolution remain unavailable.
