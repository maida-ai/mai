# Authority startup foundation

The startup foundation implements authority creation and evidence-bound reconciliation. Fresh authorities reject pushes until explicit receive enablement. The engine also supports explicit serial integration of named generations; this is not automatic scheduling. Startup tests and enabled-path interruption tests use real Git, SQLite and process termination, not a power-loss guarantee.

An authority contains `authority.git`, `.mai/config.toml` and `.mai/state.db`. The local TOML configuration binds format version 2, a unique authority identity and the exact import baseline to immutable database metadata. The authority-bound ordinary lease store also uses format 2 and is required; missing or copied mismatched lease state refuses startup. Unsupported or incomplete formats fail with recovery guidance; there is no conversion. Recreate only disposable evaluation authorities when moving from older formats; preserve real work and old state for inspection. Imported HEAD becomes r0 unchanged, including its original history. Empty initialization creates a deterministic empty baseline. Initializers validate the source and the independently cloned staged copy, so an unsupported source change during clone cannot bypass scope validation. The destination must be absent or empty; files are installed with exclusive creation, leaving `.mai-initializing` on interrupted installation. Preserve incomplete directories for investigation and initialize a new empty destination instead of deleting or repairing unknown data automatically.

`Authority::open` checks configuration, schema, identity and baseline without reconciling. Callers of `Authority::reconcile` must hold the exclusive OS lock on `.mai/engine.lock`; the engine obtains ownership before opening state, and repeated initialization acquires the same lock before reconciliation. Stale PID text never proves ownership, and the lock file is persistent. Local filesystem ownership is not a security boundary.

The first-parent trunk ledger must reach the exact recorded r0. Each subsequent ordinary landing must have one parent and unique `Mai-Generation` (compact JSON containing `change_id` and `generation`), `Mai-Attempt`, `Mai-Revision: rN` and `Mai-Policy` trailers. Reconciliation verifies stored consecutive revisions; it never supplies a missing revision by counting history. `Change-Id` alone cannot identify a generation. The exact commit, tree, parent, submitted generation/commit, attempt and trusted-policy identity must match immutable successful validation evidence retained before CAS. An unrecognized or contradictory trunk commit freezes startup for investigation. Future upstream-sync merges and full provenance/trailer emission require #34/#61 qualification; this foundation does not accept arbitrary merge parents.

Every persisted submission keeps `refs/mai/changes/<change_id>/<generation>` pointing to its exact submitted commit. Missing acknowledged retention is an error. Candidate refs use `refs/mai/candidates/<change_id>/<generation>/<attempt>` and can be restored only from retained exact candidate objects and immutable evidence. Historical candidate refs/evidence remain retained; they cannot qualify a later attempt. After verified landings are recorded, remaining interrupted validations retire their attempt and requeue the same generation subject to lifecycle dependency state. Repeated startup creates neither a new generation nor a duplicate terminal outcome.

For a recognized landing, the actual parent-to-tree diff is recomputed with rename collapsing disabled. Raw path bytes are sorted and encoded as the ADR 0004 canonical `file:` units, then compared with retained evidence. Missing landed records in `refs/notes/mai-objects` can be reconstructed with exact object/generation/revision associations and explicit `mvp-file-only` fallback. Existing records for another phase are preserved; contradictory or malformed notes fail rather than being overwritten. The SQLite unit index is rebuildable from verified landing associations. The explicit receive/integration paths compute file manifests and enforce trusted policy; upstream-sync provenance and the wider queue remain separate work.

Validation covers new/imported/repeated initialization, preserved user files, corrupt and mismatched state, live and stale locks, fail-closed receive, wrong or copied identities, missing retention, failed validation, false manifests and conflicting notes. Separate subprocesses are killed before CAS, after CAS, after notes and after state completion, then restarted twice to inspect convergence. This establishes finite process-interruption behavior only. Native Windows and macOS results must come from their CI runs; Linux tests do not infer their success. Enabled receive and integration paths have their own finite interruption tests; broader crash coverage remains tracked under #60/#61/#69.

Authority directory names follow the host filesystem's supported names. Valid Unicode directory paths are exercised on every supported platform; Linux also exercises non-UTF-8 directory names. The native macOS filesystem rejects invalid UTF-8 names, and its regression verifies explicit rejection without modifying user data or creating an import destination. This filesystem constraint does not change canonical Git-tree path-byte identities, which are qualified separately using Git plumbing without requiring checkout materialization.
