# Recorded local benchmark evidence

The recorded Rust JSON retains the original unreleased `0.2.0` label used when these measurements were collected. The project version has since been reset to `0.0.1` for the MVP; this label is historical evidence, not a released version or the current version. Python baseline labels likewise remain historical.

These are individual development-host samples, not performance guarantees. These samples describe only the retained worktree engine, not the proposed rewrite; see [rewrite success measurements](../../docs/project.md#success-measurements) for the new qualification goals. The Python baseline was recorded before implementation removal; Rust `core` samples use direct library calls and `cli` samples launch the native executable. All Rust samples use an optimized release build with committed Git fsync. CPU/RSS information is in sibling GNU time `.resources` logs, including setup and verification.

The initial 1/16/64-agent and 1,000-file samples predate addition of admission queue and accepted-history integrity fields to the harness; their original JSON is preserved. Both recorded 16-agent modes and the 64-agent run completed their expected workloads. Repeated high-population samples use the corrected reporter, which emits JSON even when overload prevents all requests from completing. Initial high-population reporter-abort samples were replaced by corrected reports rather than being treated as valid throughput measurements.

Hardware: AMD Ryzen 9 7950X, 16 physical cores/32 logical CPUs. Software: Linux 7.0.0-34-generic x86_64, Git 2.43.0, Rust/Cargo 1.97.0. Source filesystem: ext4 on NVMe. Workloads use temporary directories on `/tmp`, a separate ext4 filesystem on `/dev/nvme0n1p1` (89% used at inspection); this environment's filesystem details and uncontrolled caches/background work limit comparability. Some early sample workloads overlapped development compilation or another workload. Benchmark worker count is bounded (8 or 16), distinct from population.

For independent reproduction, run the matrix without concurrent development work, capture machine/mount/tool versions and repeated runs, and retain failed workload output. A full-workload failure is operational evidence even if accepted history is intact. No remote clients, network latency, auth, daemon, production codebase, or power-loss performance is represented.

The corrected 256-agent/16-worker disjoint sample accepted 248 and rejected eight requests at the contention budget, at 17.22 accepted revisions/s. The mixed sample with 64 hotspot agents accepted 186, rejected 63 true conflicts, and rejected seven requests at the contention budget, at 17.54 accepted revisions/s. Both retained contiguous accepted history and accepted file contents (`publication_integrity_ok:true`), but both failed full-workload completion (`integrity_ok:false`).

The 1,024-agent/16-worker disjoint sample accepted 978 and safely rejected 46 at the contention budget. Accepted history/content remained intact, but full-workload completion failed. Submission throughput was 14.12 accepted revisions/s, service p95 4,802.73 ms and p99 6,688.09 ms, burst p99 68,149.81 ms, admission queue p95 62,951.63 ms, workspace setup 50.459 seconds, and accepted-request retry count 7,355. GNU time reported 95.07 seconds user CPU, 205.14 seconds system CPU, 232% CPU utilization, and 2:09.38 elapsed for the complete workload. This is evidence of retry/fairness and materialization limits, not qualification for thousand-agent simultaneous publication.

Full-hotspot CLI samples completed with exactly one winner: 16 agents/16 workers rejected 15 conflicts; 64 agents/16 workers rejected 63; 1,024 agents/16 workers rejected 1,023. All reported both integrity checks true with no other errors. The 1,024-hotspot sample took 51.694 seconds for workspace setup and 1.790 seconds for submission processing, with service p95 34.49 ms. Fast conflict rejection does not establish independent-publication capacity. The final 16/64 full-hotspot samples were run after moving revision counting before publication and adding registry-symlink rejection; earlier samples use the same prepare/revalidate/CAS/fsync design.
